## 0. 结论

**不建议按当前状态合并或发布 PR #4。** HEAD `5e8a2d0` 的 CI 是 20/20 全绿、现有 1,117 + 208 个 Python 测试与 159 个 Node 测试也全绿，但本次独立审计在测试盲区中发现 **3 个 P0、23 个 P1（去重后）**，其中至少 3 条会造成不可逆正文/证据丢失或主路径 100% 失败：

## 2. P0（3 条，全部已复现）

### C-01 [P0] `confirm_fact` 双定义：作者确认接口 100% 500，权威提升链路整体失效

- **位置**：`backend/integration/world_state.py:214-224`（第一定义，带 `authority_level` 与 `pending_confirm` 校验）、`world_state.py:559-560`（第二定义覆盖前者）；`world_state.py:563-564` 的 `reject_fact` 同样被覆盖；调用方 `backend/manager/api_v09.py:61-66`。
- **机制**：Python 后定义覆盖前定义。`api_v09` 固定传 `authority_level=`，运行时解析到第二定义，直接 `TypeError: unexpected keyword argument`。第二定义只把状态设为 `active`，不提升 `authority_level`；`reject_fact` 第二定义把状态写成 `superseded` 而非 `archived`，且不要求原状态为 `pending_confirm`。
- **影响**：作者点「确认」永远 500；`pending_confirm` 事实只增不减；`build_context` 的 L2 只收 `pinned/author_locked/confirmed_prose/published_prose`，AI 提取事实永远进不了长期记忆层；异常文本还会被 `app.py:1306-1308` 原样返回。
- **证据**：`tmp-c-platform/t1_world.py` 输出 `CONFIRM RAISED: TypeError ...`；真实 FastAPI `t20_realapp2.py` 输出 `CONFIRM: 500`。
- **最小修复**：删除 559-564 的第二定义，保留第一定义的校验语义；`reject_fact` 恢复 `archived` 与 `pending_confirm` 前置；补「确认后 authority 必须提升」的回归测试。

### C-02 [P0] 写事务内嵌套 `write_tx`：同线程自锁死，15–76 秒后 500

- **位置**：`backend/integration/quality.py:126` → `136`；`world_state.py:615` → `619`；`annotations.py:177` → `183`，以及 `509/524/665`；根因 `workbench_db.py:100-131`（每次新连接 `BEGIN IMMEDIATE`）与 `workbench_db.py:511-521`（`chapter_uid` 无行时再开 `write_tx`）。
- **机制**：外层 `with wb.write_tx` 已持有 SQLite 写锁；`chapter_uid()` 另开连接再 `BEGIN IMMEDIATE`，SQLite 不识别同线程重入，等 `busy_timeout=15000ms`；`write_tx` 外层还有 5 次重试，合计约 76 秒，最后 `database is locked`。`import_chapters` 走 `versions.commit_raw_bytes`，不建 `chapter_meta`，因此任何「导入旧稿」创建的书立即命中。
- **影响**：导入旧稿后的第一次质量体检、书级改令豁免、整章批注三条作者可见链路直接 500；写锁期间其他写请求排队，放大为全站卡顿。
- **证据**：`tmp-c-platform/t15_nested.py` 输出 `add_exemption -> database is locked (15.0s)`、`review -> ... (75.9s)`；`t36b_import.py` 导入 2 章后 `chapter_meta rows: []`，`review` 76 秒失败。
- **最小修复**：在进入 `write_tx` 之前计算 `chapter_uid`（`build_context` 已这样做），或实现线程本地可重入 `SAVEPOINT`；在 `write_tx` 入口接入 `lock_manager` 的 SQLite 嵌套守卫。

### C-03 [P0] GC 删除仍在使用的批注基线快照与待审修订预览（不可逆数据丢失）

- **位置**：`backend/integration/maintenance.py:21`（`_PREVIEW_DIRS` 含 `snapshots`、`revision_previews`）、`38-58`（保护面只有 `artifact_refs`）、`74-111`（删除）；快照写入 `annotations.py:50-80,154,172`；修订预览 `revision_plan.py:284-332`。
- **机制**：`_protected_paths` 只信任 `artifact_refs.ref_count>0`/`protected=1`；但 `register_artifact` 在生产代码中零调用，`artifact_refs` 永远为空。`save_snapshot` 写 `.webnovel/snapshots/<sha>.txt` 并在 `annotations.base_snapshot_id`/`preview_index` 中引用，却从不登记 artifact；GC 把这些文件当无引用预览，超过 `min_age_seconds`（API 下限 1 天，默认 7 天）后物理删除。
- **影响**：`apply_hunks`、`undo_apply`、`run_annotations`、`revision/accept` 读基线时 `snapshot_missing`（404），已写好的批注/修订证据无法应用或撤销；待审预览从列表消失且不可重建。与模块 docstring「绝不碰批注证据」相反。
- **证据**：`tmp-c-platform/t10_gc.py` 输出 `GC removed: 1`、`read_snapshot -> AnnotationError snapshot_missing`；真实 HTTP `t20_realapp2.py` 输出 `gc real: 200 1 snapshot exists: False`。
- **最小修复**：把 `snapshots`、`revision_previews` 从 `_PREVIEW_DIRS` 移出；GC 只删在 `annotations`/`preview_index`/`revision_plan` 中无引用且过期的对象；`save_snapshot`/`save_preview` 调 `register_artifact(..., ref_count=1)`，或直接按 SQLite 引用表计算保护集。
